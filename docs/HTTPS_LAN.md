# HTTPS on your LAN

Native HTTPS uses the same gateway routes and authentication as HTTP. It does
not require a public tunnel or a reverse proxy. With HTTPS enabled, the configured
LAN address listens on HTTPS port 8443; HTTP port 8045 listens on `127.0.0.1` only.
Local clients and authenticated internal warmup can continue using HTTP loopback.
LAN HTTPS requires authentication even if the saved auth preference is Off.

Create a private local CA and a server certificate with Subject Alternative Names
for your LAN IP, `localhost`, and any hostname you use. For example, the current
LAN IP `192.168.0.168` must be an **IP SAN**, not a DNS SAN. Add `127.0.0.1` and `::1`
if clients will use those HTTPS addresses. Keep the CA private key offline/private;
only the CA public certificate is distributed to clients. This app does not issue
or automatically renew certificates.

Close the gateway before importing or rotating an identity. Both executable
variants support this local command, which exits without starting the gateway or
contacting an AI provider:

```text
antigravity-server tls-import --cert /absolute/path/gateway-chain.pem --key /protected/path/gateway-key.pem --advertise 192.168.0.168 --port 8443
```

Use `antigravity-tools tls-import` for the desktop executable. The certificate
chain PEM contains the leaf first, followed by intermediate certificates. The
unencrypted private-key PEM can be PKCS8, PKCS1, or SEC1. The command validates
the matching pair before writing, stores the private key in the OS credential
store, and saves only its immutable reference and the public certificate path in
configuration. Keep the public certificate file in place. Remove the temporary
private-key file yourself only after a successful import. Old native-store key
generations are retained so a stale running configuration cannot lose its key.
Do not use files from `proxy/testdata` for a real gateway.

Restart the application and use `https://192.168.0.168:8443`. The listener must
still be bound to the LAN address, or `0.0.0.0`; HTTPS does not widen a loopback
bind. Allow the HTTPS port through the host firewall for your LAN/VPN only. Do not
forward it publicly through your router.

Install the **public CA certificate** into each client's trusted root store using
that operating system's certificate settings. Some applications maintain their
own root store; configure their documented CA certificate setting. Node clients
can use `NODE_EXTRA_CA_CERTS=/path/to/public-ca.pem`, and Python Requests clients
can use `REQUESTS_CA_BUNDLE=/path/to/public-ca.pem`. A client connecting by an IP or
hostname absent from the certificate SAN must fail. Never disable certificate
verification. The certificate must remain valid and be renewed before expiry.

The contextual HTTPS settings live beside LAN binding in API Proxy settings.
Changes to binding, ports, or identity require a full application restart; stopping
and starting the proxy's inference service alone does not recreate its management
listener. The running status advertises the live HTTPS URL; the local HTTP URL
remains separate for internal use.

Headless configuration uses `proxy.tls`:

```json
{
  "enabled": true,
  "port": 8443,
  "certificate_path": "/absolute/path/gateway-chain.pem",
  "advertised_host": "192.168.0.168",
  "private_key_ref": { "version": 1, "generation": "generated-by-tls-import", "parts": 1, "digest": "generated-by-tls-import" }
}
```

The reference is generated by `tls-import`; do not invent or copy it between OS
users/machines. An explicit operator-managed `private_key_path` is also supported,
with owner-only permissions on Unix (`chmod 600`) and a private ACL on Windows.
There is no fallback from a missing/inaccessible native key to a plaintext file.
Headless environment overrides are `ABV_TLS_ENABLED`, `ABV_TLS_PORT`,
`ABV_TLS_CERT_PATH`, `ABV_TLS_KEY_PATH`, and `ABV_TLS_ADVERTISED_HOST`. An explicit
key-path override selects that file instead of the managed reference. These
options never accept private-key contents as arguments or environment variables.

TLS accepts HTTP/1.1, including SSE and WebSocket upgrades. Incomplete handshakes
are bounded to ten seconds and at most 128 concurrent attempts. HTTP/2 is not
advertised. Certificate/key files are bounded to 64 KiB; identity or bind errors
stop startup rather than exposing a LAN HTTP fallback.
